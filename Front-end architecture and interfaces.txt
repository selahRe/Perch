先前大致设定
Ai桌面宠物
一只猫在桌面上根据用户的工作时间的输入，选择状态进行智能互动，他会弹出对话框和主人互动。用ai判断桌宠是否出现。
功能：
前端api：
宠物显示/隐藏
宠物情绪图切换：happy / eat / play（默认 happy）
对话框显示/隐藏
对话框内容：有字 / 无字（空字符串就是无字）
后端：
监控用户工作状态
调用AI API
处理AI返回的决策
保存用户数据到本地
定时检查是否该提醒

2. 架构约定
通信方式
使用 Electron IPC：
后端：Electron main process
前端：Electron renderer process
约定原则
后端负责决策
是否出现
说什么
当前情绪状态
是否触发提醒
前端负责展示
显示/隐藏宠物
切换动画状态
显示/隐藏气泡
渲染问卷和设置页
前端不直接访问系统 API
所有系统、存储、AI 相关逻辑走主进程
3. 统一状态模型
前端内部维护一个统一 UI 状态：
{
 "petVisible": true,

 "chatVisible": true,
 "message": "该休息啦～",
 "userProfile": {
   "name": "Chloe",

   "freeTime": "20:00-22:00",
   "reminders": {
     "hydration": true,
     "stretching": false,
     "meetings": true
   }
 },
 "settings": {
   "reminderEnabled": true,
   "dataCollectionEnabled": true
 }
}
4. IPC 通道设计总览
后端 → 前端
4.1 pet:update
用于更新桌宠显示状态、情绪、气泡文本。
这是最核心事件。
4.2 reminder:trigger
用于触发提醒气泡。
如果你们想精简，其实可以并入 pet:update。
4.3 settings:loaded
后端把已保存的用户设置发给前端。
4.4 profile:loaded
后端把已保存的 onboarding 信息发给前端。
前端 → 后端
4.5 profile:save
保存初始化问卷信息。
4.6 settings:save
保存设置页信息。
4.7 pet:interaction
前端主动告诉后端用户点击了喂猫/玩耍。
4.8 app:ready
前端启动完成，请求后端下发初始数据。
5. 详细接口定义
5.1 app:ready
方向
前端 → 后端
作用
前端启动完成后通知后端，后端随后返回：
用户 profile
用户 settings
当前宠物初始状态
请求体
{
 "timestamp": 1710000000000
}
返回方式
后端收到后，通过以下事件推送给前端：
profile:loaded
settings:loaded
pet:update

 "gender": "female",

 "reminders": {

   "stretching": false,
   "meetings": true
 }

字段
类型
必填
说明

5.6 pet:update （最重要）
方向
后端 → 前端
作用
AI 或调度器给出结果后，前端根据这个事件更新 UI。
你们 MVP 最核心就靠这个事件跑通。
数据体
{
 "visible": true,
 "emotion": "play",
 "speak": "来玩吧！",
 "reason": "user_is_idle",
 "durationMs": 5000
}
字段说明
字段
类型
必填
说明
visible
boolean
是
是否显示宠物
emotion
string
是
happy / eat / play
speak
string
否
气泡内容；空字符串表示不显示
reason
string
否
触发原因，方便日志和调试
durationMs
number
否
本次状态持续多久，前端可选是否处理
前端处理规则
条件
前端行为
visible = true
显示宠物
visible = false
隐藏宠物
emotion = happy/eat/play
切换宠物状态动画
speak != ""
显示气泡
speak == ""
隐藏气泡
示例 1：出现并说话
{
 "visible": true,
 "emotion": "happy",
 "speak": "你好呀～"
}
示例 2：隐藏
{
 "visible": false,
 "emotion": "happy",
 "speak": ""
}
示例 3：提醒
{
 "visible": true,
 "emotion": "play",
 "speak": "该站起来活动一下啦～",
 "reason": "stretch_reminder"
}

方向
前端 → 后端
作用

建议：
{

}

{

6. 推荐的前端 preload API
你可以跟后端同学约定，preload 层暴露成这种形式：
window.electronAPI = {
 sendAppReady(),
 saveProfile(profile),
 saveSettings(settings),
 sendPetInteraction(data),
 onProfileLoaded(callback),
 onSettingsLoaded(callback),
 onPetUpdate(callback),
 onReminderTrigger(callback)
}
更具体一点：
window.electronAPI.sendAppReady()
window.electronAPI.saveProfile(profile)
window.electronAPI.saveSettings(settings)
window.electronAPI.sendPetInteraction({ action: 'feed', item: 'cat_food' })
window.electronAPI.onPetUpdate((data) => {
 // 更新 visible / emotion / speak
})
7. MVP 最小闭环
你跟后端同学只要先打通这 4 个，就能跑：
前端发
app:ready
profile:save
settings:save
后端发
profile:loaded
settings:loaded
pet:update
实际上 pet:update 是唯一真正必须打通的实时事件。
8. 建议的错误处理格式
所有保存类接口统一返回：
{
 "success": false,
 "message": "failed to save profile",
 "errorCode": "PROFILE_SAVE_ERROR"
}

前端这边 MVP 先约定一个核心实时事件 pet:update。
后端只要在 main process 里根据 AI / 定时器 / 用户状态计算出结果后，
通过 IPC 给前端发：
{
 visible: boolean,
 emotion: "happy" | "eat" | "play",
 speak: string
}
前端收到后只负责：
1. visible 控制宠物显示隐藏
2. emotion 控制宠物状态切换
3. speak 控制气泡显示内容；空字符串就隐藏
另外前端会提供两个保存接口：
- profile:save 保存 onboarding
- settings:save 保存设置
前端启动时会发 app:ready，
后端可回传：
- profile:loaded
- settings:loaded
- pet:update

App.tsx
